# `@orahako/sdk`

`@orahako/sdk` is the public Orahako API v1 contract. It is the dependency used by
built-in packages and by external plugin source before it is packed into a ZIP.
Plugins run in the host JavaScript context and therefore have the same authority as
the app. A ZIP is not a security sandbox; install only code from a trusted source.

See the [architecture guide](../../../PLUGIN_ARCHITECTURE.md) for bundle
composition, root-query routing, and runtime boundaries.

## API v1 manifest

The packer reads the root `manifest.json` and uses the first existing entry in
`src/index.tsx`, `src/index.ts`, `index.tsx`, `index.ts`. It bundles source as ESM
and packages `dist/` and optional `assets/`:

```text
manifest.json
dist/index.js
dist/index.css       # only when declared/generated
dist/tailwind.css    # when generated by the packer
assets/...            # optional
```

The manifest must use `apiVersion: 1`:

```json
{
  "id": "org.example.my-plugin",
  "name": "My Plugin",
  "version": "1.0.0",
  "apiVersion": 1,
  "kind": "feature",
  "entry": "dist/index.js",
  "minAppVersion": "0.16.0",
  "inject": ["ui"],
  "providerIndependent": true
}
```

`kind` is one of `runtime`, `provider`, `feature`, `theme` or `shell`. `id` uses
lowercase dot-separated segments and `version` is SemVer. `entry`, `styles` and
`icon` are safe relative paths inside the ZIP. Optional fields are `description`,
`author`, `homepage`, `categories`, `requires`, `provides`, `configSchema`,
`nativeCapabilities`, `required` and `providerIndependent`.

The kernel rejects unsafe paths, duplicate files, missing declared files and
invalid UTF-8 in the manifest. Default limits are 20 MiB for the ZIP, 8 MiB per
file, 32 MiB total uncompressed, 512 files and 64 KiB for `manifest.json`.

- `inject` names required Cordis root services. A missing service prevents `apply`
  from running.
- `provides` names services that `apply` must publish with `ctx.set`.
- `requires` names plugin IDs and SemVer ranges; it is distinct from `inject`.
- `configSchema` is JSON Schema draft-07. The kernel validates configuration and
  applies schema defaults; an external ZIP starts with an empty configuration
  object before validation.
- `nativeCapabilities` names versioned capabilities such as
  `native.geolocation@1`. Installation checks the composition allowlist;
  the ability to call the capability still depends on the host build and permissions.

ZIPs with any other API version cannot load on API v1. Migrate the source to the
v1 contracts, rebuild the ZIP and republish it with an API v1 release entry.
Changing the number alone does not migrate the plugin.

## Defining a plugin

Save this example as `src/index.tsx` alongside the manifest above. The ZIP entry
default-exports the plugin definition; keep its manifest metadata consistent with
the installed `manifest.json`.

```tsx
import { defineDictionary, definePlugin, PLUGIN_API_VERSION } from "@orahako/sdk"

const dictionary = defineDictionary({
  zh: { title: "示例" },
  en: { title: "Example" },
})

export default definePlugin({
  manifest: {
    id: "org.example.my-plugin",
    name: "My Plugin",
    version: "1.0.0",
    apiVersion: PLUGIN_API_VERSION,
    kind: "feature",
    entry: "dist/index.js",
    minAppVersion: "0.16.0",
    inject: ["ui"],
    providerIndependent: true,
  },
  inject: ["ui"],
  apply(ctx) {
    ctx.ui.registerPage(
      { id: "index", route: "example", requiresProvider: false, dictionary },
      ({ t }) => <h1>{t("title")}</h1>
    )
  },
})
```

The definition's `inject` tuple determines which services `apply` can access.
Register resources in `apply`; use `ctx.effect` to attach cleanup for resources
that are not already scoped by the service. After side-loading, open
`/?route=example` relative to the app's base path. `requiresProvider: false`
marks the page as not requiring a Provider; `providerIndependent` keeps the
plugin running even when a school's allowlist omits it.

## UI and derived props

Page, Shell, Slot and settings components receive derived props, not `ctx`.
Their registrations can declare `dictionary`, `children`, `store` and `inject`
as needed. The sole `ui-renderer` derives four shares:

1. **Runtime share**: owner-supplied props, scoped typed translator `t`, and `locale`.
2. **Child render share** — only the declared `renderSlot` and
   `renderSlotChain` keys.
3. **Store share** — selector-based `useStore` and controlled `actions`, never
   the store instance or raw `setState`.
4. **Business inject share** — `NoInfer`-locked data/callback values and
   `use<Name>` hooks generated from `ObservableSource` values in `hooks`.

`ui-renderer` is the only module allowed to bridge observable state to React
(`useSyncExternalStore`). Components should remain ordinary, testable React
functions and should not use business React contexts or direct `useSWR`.

## Shell replacement and host preferences

A replacement shell registers the same public child slots as the default shell
(`shell.gate`, `shell.banner`, `shell.activity`, `shell.header.actions`,
`shell.sidebar.footer`, `shell.overlay`) and renders them through its derived
`renderSlot` / `renderSlotChain` props. Public shell slots are claimed in the
plugin scope and are reference-counted, so multiple shells may coexist:

```ts
const children = {
  "shell.gate": { kind: "chain" },
  "shell.banner": { kind: "list" },
  "shell.activity": { kind: "list" },
  "shell.header.actions": { kind: "list" },
  "shell.sidebar.footer": { kind: "list" },
  "shell.overlay": { kind: "list" },
} as const

apply(ctx) {
  for (const [name, spec] of Object.entries(children)) {
    ctx.slots.declare({ name: name as SlotName, kind: spec.kind })
  }
  ctx.ui.registerShell(
    { id: "community", name: "Community", children, declareChildren: false },
    CommunityShell
  )
}
```

`ShellSpec.declareChildren` defaults to `true`; in that mode the shell owns its
children and a duplicate declaration throws. With `false`, the runtime only
verifies that each declared child slot already exists with the requested kind.
Pages and settings categories continue to declare their own children and still
reject duplicates.

Shell and page contributions carry a monotonically increasing `generation`.
Error boundaries use it as their key/reset key, so a plugin that re-registers a
contribution after a failure gets a clean boundary instead of the old fallback.

The active shell and theme are host preferences, not shell-local state. The host
exposes `packageRuntime.preferenceState` (a `PluginHostPreferenceSnapshot` with
optional `activeShell` / `activeTheme`), plus
`getActiveShell` / `setActiveShell` and `getActiveTheme` / `setActiveTheme`.
`OrahakoApp` subscribes to that snapshot, so a shell change made by the plugin
manager applies immediately. Shells must not keep their own theme store or emit
a second theme `<style>` channel. When `activeTheme` is unset or empty, no theme
is injected; there is no fallback to the first registered non-empty theme.

## Stores and dictionaries

`defineStore` creates a factory, not a module singleton:

```ts
const store = defineStore({
  init: () => ({ enabled: false }),
  persist: { key: "preferences", mode: "local" },
  actions: {
    toggle: ({ get, set }) => set({ enabled: !get().enabled }),
  },
})
```

In `apply`, use `const instance = store.create(ctx.storage)` and bind disposal
with `ctx.effect(() => () => instance.dispose())`. Pass `instance` as `store` in
the UI registration. The storage runtime adds the `orahako-plugin:<plugin-id>:`
prefix; use plugin-local keys, not global storage keys.

`defineDictionary({ zh, en })` checks the bilingual message shape and narrows
dot-path translation keys when passed as `dictionary` to a UI registration.
Use scoped `ctx.i18n.register(dictionary)` when registry metadata also needs
translation keys.

## Routing and back navigation

`ctx.router` owns application history. `registerBackGuard` runs guards by descending priority and then newest registration first. Return `false` only after consuming back by closing an overlay or page-local state; return `true` when the guard is irrelevant to the active page so other guards and history can proceed. The default Shell bridges `BackLayerProvider` priorities into this API. A Shell can register an application back fallback to resolve a parent or primary page when history is exhausted; root pages deliberately have no fallback.

## HTTP and native boundaries

Call `ctx.http.send` for platform transport and register middleware with
`ctx.on("http/request", handler)` or `ctx.on("http/response", handler)` in
`apply`. The runtime runs the request waterfall before transport and the response
waterfall with the effective request afterward. A handler can return a replacement;
returning `undefined` preserves the current value.

Use `ctx.native.capabilities` to discover (`list`, `has`), acquire and invoke
versioned capabilities. `acquire` returns a release function. Handle missing Web
capabilities and device permission failures; a ZIP cannot add Android code,
permissions, receivers or widget implementations.

## External module boundary and packing

The packer externalizes exactly `PLATFORM_MODULES` from `@orahako/sdk`:

```ts
[
  "react", "react-dom", "react-dom/client", "react/jsx-runtime", "sonner",
  "@orahako/sdk", "@orahako/ui-primitives",
]
```

The loader accepts only package-relative imports and the exact bare specifiers
above. Other supported dependencies can be bundled by esbuild, but host-private
paths, `@/` aliases and Next.js imports are not part of the SDK. In particular,
`@orahako/academic-sdk` is not a shared module. Declare bundled entry CSS in
`styles`; the packer appends `dist/tailwind.css` when it generates utilities.

From the repository root:

```sh
pnpm plugin pack <plugin-directory> [output.zip]
```

The command validates the manifest, bundles ESM with esbuild, builds Tailwind
utilities when needed, validates the ZIP and prints its path, byte size and
SHA-256. By default the output is `<plugin-id>-<version>.zip` in the source
directory. For a concrete example:

```sh
pnpm plugin pack packages/plugin-template /tmp/orahako-hello.zip
```

Market indexes keep `schemaVersion: 1`; individual releases declare
`apiVersion: 1`, `version`, `platforms` (`web` or `android`), `zipUrl`, `sha256`,
`size` and `publishedAt`. Set `minAppVersion` to the oldest compatible app
release if needed. Compatibility is filtered by API, platform, app version and
native capabilities before selecting the highest matching SemVer. Publish the
exact ZIP under `dist/plugins/<id>/<version>.zip` in
`Youwenqwq/orahako-plugin-registry`, update its registry source, and commit the
generated `dist/plugins.json`. The app reads both index and ZIPs from that
repository's `main` branch through GitHub Raw.

## Verification

For repository changes, use the focused checks first and then the complete gate:

```sh
pnpm run typecheck
pnpm run lint
pnpm run test
pnpm run verify-architecture
pnpm run build
pnpm plugin pack <plugin-directory> [output.zip]
```

Android composition checks are separate:

```sh
pnpm run build
npx cap sync
cd android && ./gradlew verifyNativeComposition testDebugUnitTest
```
